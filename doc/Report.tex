\section{Assembler Implementation}

Our assembler is composed of three main components: the emulate file, where
instruction fetch and encode is performed; the modules, which consist of 
all instruction-encoding functions; and the data structures. The first data 
structure is the dynamic \texttt{symtable}, a dictionary of labels to addresses. 
The second data structure is the alias table, a dictionary of mnemonics to 
function pointers where the instruction type is handled. 

This assembler utilizes two-pass assembly. The function \texttt{first\_pass} 
loops through each line of the input assembly file, storing labels and their 
corresponding addresses in a symbol table. Next, the function 
\texttt{second\_pass} accesses each line of the assembly file again, tokenising each 
line to identify the instruction name, replace labels with offsets, and 
extract instruction parameters. The instruction name is then inputted to the alias
table's lookup function, which returns a function pointer to the proper encode function. 
For example, inputting the \texttt{add} instruction to lookup table 
returns a pointer to function \texttt{arith} in module \texttt{data-processing}. 
Each of these functions takes the list of tokens, the size of the token list, 
and an integer pointer to where the encoded instruction is to be stored. The integer 
pointer's contents are updated based on the instruction type and tokens. 
Each function also returns a status code indicating encoding success, either 
\texttt{EXIT\_SUCCESS} or \texttt{EXIT\_FAILURE}. Lastly, the encoded instruction
is converted to binary and written to the specified output file. 
Note that in the second pass, any line consisting of only a label, directive, 
or newline is automatically skipped. 

While writing our assembler, we learned to appreciate the importance of fleshing out 
useful data structures before implementing other functionality. For example, 
the dynamic symbol table was originally fixed-length, which is inefficient 
given there could be any number of labels in an assembly file. Also, the
table initially stored addresses as integer pointers instead of just integers, 
which caused issues when looking up addresses using labels. Thus, thorough brainstorming, 
testing, and review are always necessary before a data structure is deployed. 
In addition, our group focused on the challenging implementation task we identified 
last week: writing utility functions early on. Throughout the assembler task, 
any function that seemed usable in multiple modules -- like extracting immediate 
values and register numbers -- were written in a file called \texttt{assembly-utils.c}. 
As a result, many of our tasks were simplified, and we enjoyed more efficient development. 

\section{Blinking LED Implementation}

To implement Part III, we began by building a simple circuit with one red LED, one 220\(\Omega\) resistor, one wire to ground, and one wire to the output at GPIO pin 3. Then, we made a file, \texttt{led\_blink.s}, in which we started to write our assembly code. Our assembly code has five main sections: \texttt{setout}, \texttt{sethigh}, \texttt{setlow}, \texttt{wait}, and a section for integer directives.

In the first section, \texttt{setout}, we select pin 3 as the output by setting FSEL3 to binary 001 and storing this value in the given GPIO function selection address.

The next section, \texttt{sethigh}, turns the LED on by storing \texttt{0x8} in the GPSET0 register address, which sets the bit corresponding to pin 3. Additionally, we set an “LED state” flag in register \texttt{w9} to signal that the current state is high before branching to the \texttt{wait} section of the code. Similarly, the \texttt{setlow} section turns the LED off by storing \texttt{0x8}  in the GPCLR0 register address, setting the bit corresponding to pin 3 of the CLEAR register. This time, we set the “LED state” flag register to 0 to signal that the current state is low before branching to \texttt{wait}.

In the \texttt{wait} section of our code, we use a loop to wait for a fixed amount of time before updating the output signal. First, we reset the loop by setting register texttt{w3} to 0. Within the loop, we add 1 to register \texttt{w3} until it is greater than or equal to a set wait time of 0x50000. Once the wait time is reached, we check the “LED state” flag register to see if the current state is high or low, branching to the next state depending on the outcome of the comparison.

The final section of our code includes a set of seven integer directives that are loaded into registers at the start of the program. The integer directives include the GPIO function select address, the GPSET0 address, the GPCLR0 address, the wait time, the GPIO configuration for function selection, the GP output configuration for sending high/low signals, and the “LED state” flag.

We faced many challenges while writing our assembly code. For example, our attempts to use the \texttt{mov} instruction to load an immediate value into a register yielded incorrect results, which confused us greatly. When we finally realised that our emulator and assembler do not support the functionality for immediate operands in \texttt{mov} instructions, we changed the structure of the code to use the \texttt{ldr} instruction combined with integer directives to store the set and clear flags in the corresponding GPIO output registers. When using a \texttt{mov} instruction, we used register operands rather than immediate values.

Another challenge we faced was understanding the assembly we had written. Since our assembler does not support comments, descriptive variable names and labels were essential to code clarity. However, when we began writing the code, our variable names were extremely generic, causing confusion and many delays in debugging. Therefore, we altered our code to have clear labels for different sections and comprehensible integer directive names, resulting in a more productive debugging process. 


\section{Text-Based Virtual Pet}

A “virtual pet” is a digital toy that often requires care and attention. The most popular 
example is Bandai Namco’s Tamagotchi, a physical toy with a few interaction buttons 
and a digital screen where the “pet” is displayed. Similar to a Tamagotchi, our text-based 
virtual pet extension requires players to feed, clean, and play with their pet to keep their 
pet happy and alive. However, our implementation also includes an ``interaction limit'' 
to prevent users from becoming addicted or dependent on their virtual pets. Hence, our 
virtual pet extension can be used as a fun way to help children and teens practice 
responsibility and balance; although users should check on and care for their virtual 
pet every once in a while, they are not allowed to spend the entire day focusing only 
on their pet. This concept can then be generalized to any aspect of life, including 
studies, self-care, hobbies, and more. 

\subsection{Virtual Pet Design}
The virtual pet has three main categories that the user can interact with: cleanliness, happiness, and hunger. Each category decrements by one bar over a fixed amount of time, but can be improved by the user through keyboard inputs. If any category reaches zero, the current virtual pet cannot continue and the user would need to leave the game or restart with a new virtual pet. 

We allowed the user to display their current category scores at any point, so they can check if any categories need particular attention. The program automatically warns the user if any category has only one heart remaining. Furthermore, we designed in-game coins that are regularly rewarded to the user if they keep their pet alive; these coins can be used to purchase gifts for and boost the happiness of their virtual pet. We later added levels as a way of encouraging user interaction; the longer a player plays for, the higher the level they can reach.

\subsection{Challenges} 
Initially, we ran into some problems implementing the pet as a global structure pointer. Eventually, we realised the main issue was how the files were linked, which led to multiple declarations of the same variable. We fixed it by ensuring the virtual pet would only be created once, at the start of the program. This proved particularly helpful when we implemented in-game coins as a separate global variable, which involved some similar C syntax.


\subsection{Testing}
When we started designing our extension, we made a list of desirable functionalities which we wanted the program to achieve by the end of the project. These included the user being able to interact with the virtual pet through the keyboard, the various category stats (such as happiness) to decrease at regular time intervals, and each category being limited to a number of hearts between zero and five. Later, we referred back to this checklist to thoroughly test the program. 

Firstly, we confirmed that the stats would decrease at the expected regular intervals (every 12 seconds for cleanliness, 8 seconds for happiness, and 5 seconds for hunger) by starting the game, then not interacting with the category currently being tested. We printed the stats at the expected time intervals, to test if the stat for the current category was decrementing each time, and observed the final output that the virtual pet had died when the category had reached zero hearts. To test the user inputs (for example, typing ‘f’ or ‘F’ should increase the hunger score), we waited for a particular category to have fewer than five hearts (outputting the stats first, to confirm this was the case), then input the appropriate character to test that we got an output message stating this category had increased as expected.

We performed many more manual tests, to determine whether the program worked as expected. In future we would test more rigorously by creating a test suite, as was used for the emulator and assembler, so that we could test many possible states of our program and ensure that it always operates in a predictable and desirable way. Due to time restrictions in this project, we decided it would be better to test the program in some of the most likely scenarios, and confirm if the main modules (such as user input) worked rather than risk running out of time building a test suite and being unable to test anything at all.
